## 1. Office-Hours 模板

### 用途
在进入正式规划之前，重新审视产品想法的根基，确保从源头方向正确。

### 6 个强制问题

| # | 问题 | 目的 |
|---|------|------|
| 1 | **用户是谁？** 精确描述目标用户画像和使用场景 | 避免做给"所有人"的产品 |
| 2 | **要解决什么痛点？** 具体描述现有解决方案的不足 | 验证需求真实性 |
| 3 | **成功的衡量标准是什么？** 可量化的指标 | 建立可验证的成功标准 |
| 4 | **为什么是现在？** 市场窗口、团队优势、技术成熟度 | 验证时机合理性 |
| 5 | **最小可行方案是什么？** 最简功能集 | 防止范围蔓延 |
| 6 | **最大风险是什么？** 技术/市场/执行风险 | 提前识别关键风险 |

```markdown
# Office Hours 模板

## 参与者
- 产品负责人（主持）
- 核心团队代表
- 可选：CEO/创始人、目标用户代表

## 会议流程（60 分钟）

### 阶段 1：问题陈述（10 分钟）
- 介绍产品背景和目标
- 明确本次 office-hours 的具体范围

### 阶段 2：6 个强制问题讨论（45 分钟）

#### Q1: 用户是谁？
- 用户画像：[描述目标用户群体]
- 使用场景：[描述具体使用场景]
- 验证方式：[如何验证这些假设]

#### Q2: 要解决什么痛点？
- 现有解决方案：[描述竞品或现有方案]
- 不足之处：[具体说明问题]
- 证据：[用户访谈、数据、案例]

#### Q3: 成功的衡量标准是什么？
- 核心指标：[至少 3 个可量化指标]
- 目标值：[具体的数字目标]
- 测量方法：[如何跟踪这些指标]

#### Q4: 为什么是现在？
- 市场窗口：[当前市场机会]
- 团队优势：[为什么这个团队能做好]
- 技术成熟度：[相关技术是否就绪]

#### Q5: 最小可行方案是什么？
- 核心功能：[不超过 5 个功能点]
- MVP 定义：[最简可行产品范围]
- 排除功能：[明确不做什么]

#### Q6: 最大风险是什么？
- 技术风险：[架构、技术选型风险]
- 市场风险：[用户接受度、竞争风险]
- 执行风险：[团队、资源、时间风险]

### 阶段 3：决策（5 分钟）
- 通过/需要修改/放弃
- 下一步行动

## 输出物
- 经批准的 office-hours 输出文档
- 明确的后续行动项
```

## 2. Plan-CEO-Review 模板

### 用途
从 CEO/创始人视角评审计划，确保与公司战略一致，评估资源投入的优先级。

### 4 种范围模式

| 模式 | 描述 | 适用场景 |
|------|------|----------|
| **Hundred** | 100 分资源投入 | 战略级项目，公司核心业务 |
| **Fifty** | 50 分资源投入 | 重要但可延迟的项目 |
| **Twenty** | 20 分资源投入 | 实验性、小型功能 |
| **Five** | 5 分资源投入 | 快速验证想法 |

# Plan CEO Review 模板

## 范围模式选择

在开始评审前，明确项目的范围模式：

| 模式 | 资源投入 | 团队规模 | 时间范围 |
|------|----------|----------|----------|
| Hundred | 100% | 5+ 人 | 1-2 个季度 |
| Fifty | 50% | 2-3 人 | 0.5-1 个季度 |
| Twenty | 20% | 1-2 人 | 2-4 周 |
| Five | 5% | 1 人 | 3-7 天 |

## 评审维度

### 1. 战略一致性
- 与公司使命/愿景的关系
- 与当前季度目标的关联
- 对核心业务指标的影响

### 2. ROI 评估
- 预期回报（收入、用户增长、效率提升）
- 投入成本（人力、时间、基础设施）
- 回报周期

### 3. 机会成本
- 如果不做这个项目，会失去什么？
- 替代方案是什么？
- 与其他项目的优先级比较

### 4. 风险评估
- 市场风险
- 执行风险
- 声誉风险

## 评审会议议程（30 分钟）

### 议程
1. **背景介绍**（5 分钟）
   - 项目概述
   - 选择该范围模式的原因

2. **战略价值阐述**（10 分钟）
   - 与公司战略的关联
   - 预期影响和回报

3. **资源需求说明**（10 分钟）
   - 人力需求
   - 时间线
   - 预算需求（如有）

4. **Q&A 和决策**（5 分钟）
   - 批准 / 需要修改 / 拒绝

## 3. Plan-Design-Review 模板

### 用途
评审设计方案，从用户体验、技术可行性、商业价值等多维度进行 0-10 评分。

### 0-10 评分体系

| 维度 | 权重 | 评分说明 |
|------|------|----------|
| **用户体验** | 25% | 易用性、可访问性、学习曲线 |
| **设计一致性** | 20% | 与现有产品风格、品牌的一致性 |
| **技术可行性** | 20% | 实现难度、依赖关系、复杂性 |
| **商业价值** | 20% | 对业务目标的贡献、收入潜力 |
| **创新性** | 15% | 差异化、竞争优势 |

### 评分标准

| 分数 | 等级 | 说明 |
|------|------|------|
| 9-10 | 卓越 | 远超预期，值得作为标杆 |
| 7-8 | 优秀 | 满足所有标准，可以开始开发 |
| 5-6 | 良好 | 基本满足，需要小幅改进 |
| 3-4 | 一般 | 存在明显问题，需要重大修改 |
| 1-2 | 差 | 不满足基本要求 |
| 0 | 不可行 | 不推荐实现 |

# Design Review 模板

## 评审准备

### 必需材料
- [ ] 设计稿（高保真原型或详细设计文档）
- [ ] 用户流程图
- [ ] 设计规格说明
- [ ] 与现有设计的对比分析

### 评审前检查
- [ ] 设计已通过内部团队评审
- [ ] 关键用户流程已走通
- [ ] 边界情况和错误状态已覆盖

## 评分环节

### 评分维度

#### 1. 用户体验（25%）
| 评分 | 标准 |
|------|------|
| 9-10 | 用户无需学习，流程直观自然，符合直觉 |
| 7-8 | 需要少量学习，整体流畅 |
| 5-6 | 有一定的学习成本，但可接受 |
| 3-4 | 需要较多指导，流程不够顺畅 |
| 1-2 | 流程混乱，用户体验差 |

#### 2. 设计一致性（20%）
| 评分 | 标准 |
|------|------|
| 9-10 | 与品牌完美融合，视觉语言统一 |
| 7-8 | 基本一致，仅有微小偏差 |
| 5-6 | 部分不一致，需要调整 |
| 3-4 | 与现有风格有冲突 |
| 1-2 | 完全偏离品牌设计语言 |

#### 3. 技术可行性（20%）
| 评分 | 标准 |
|------|------|
| 9-10 | 现有技术栈完全支持，实现简单 |
| 7-8 | 需要少量新技术，学习成本低 |
| 5-6 | 有一定复杂性，但可实现 |
| 3-4 | 技术挑战大，需要较多时间 |
| 1-2 | 技术上不可行或成本过高 |

#### 4. 商业价值（20%）
| 评分 | 标准 |
|------|------|
| 9-10 | 直接贡献核心业务指标，ROI极高 |
| 7-8 | 对业务目标有明显贡献 |
| 5-6 | 有一定价值，但不紧急 |
| 3-4 | 价值有限 |
| 1-2 | 几乎没有商业价值 |

#### 5. 创新性（15%）
| 评分 | 标准 |
|------|------|
| 9-10 | 具有行业领先性，差异化明显 |
| 7-8 | 有一定创新，优于竞品 |
| 5-6 | 与行业标准持平 |
| 3-4 | 落后于市场常见方案 |
| 1-2 | 完全同质化，无差异化 |

## 5. 完整 Sprint 模板链

### Sprint 生命周期

```
Day 1                Sprint 中期              Sprint 结束

                    │  Retro  │ <------   │  Ship   │
                    │         │           │         │
                    └─────────┘           └─────────┘
```

### Sprint 模板详细流程

#### Phase 1: Office Hours（Day 1）

**触发条件：** 新需求或重大变更

**参与角色：**
- 产品负责人（主持）
- 核心团队代表

**输出：** Office Hours 文档

#### Phase 2: Plan（Day 2-3）

**包含两个子阶段：**

**2a. CEO Review**
- 评审人：CEO/创始人
- 输出：范围模式决策

**2b. Engineering Review**
- 评审人：架构师 + 开发负责人
- 输出：架构锁定、测试矩阵

**触发条件：** Office Hours 通过

#### Phase 3: Design（Day 4-7）

**包含：**
- Design Review（0-10 评分）
- UI/UX 设计
- 设计规格文档

**触发条件：** Plan 阶段完成

#### Phase 4: Ship（Day 8-12）

**包含：**
- 迭代开发
- 持续集成
- 测试执行
- 预发布验证

**触发条件：** Design Review 通过（≥7分）

#### Phase 5: Retro（Sprint 结束后 1 天）

**包含：**
- Sprint 回顾
- 改进项识别
- 文档更新
